## Provenance & calibration
Kenya Airways did not provide operational data, so this dataset is
**synthetic**, per Proposal Section "Data Requirements." It is calibrated
against publicly known reference points rather than pulled live:
- Corridor distances (Mombasa Rd–JKIA, Westlands–JKIA, etc.) approximate
  real road distances in the Nairobi metro area (stand-in for OpenStreetMap
  routing data).
- Flight volume, destinations, and timing patterns approximate a
  mid-sized African carrier's schedule (stand-in for OpenSky Network data).
- **To move from calibrated-synthetic to API-augmented-synthetic** (as your
  proposal describes), pull real historical NBO flight timestamps from the
  OpenSky Network REST API and real corridor distance/duration from the
  OpenStreetMap Overpass/OSRM API, and swap them in for the hardcoded
  `CORRIDORS` list and flight-time generation in the script. This is
  flagged as a possible extension, not required to start modelling.

## A note on model performance (read before you train)
A quick sanity check (HistGradientBoosting, untuned, 8 raw features) gets
roughly macro-F1 ≈ 0.33 on the 4-class problem out of the box — the
labels are genuinely learnable (far better than the ~0.25 you'd get from
random guessing across 4 classes) but not trivially separable, which is
realistic. Your proposal targets F1 ≥ 0.80. Getting there is your actual
modelling work in Chapter 5 — grid search, class-weighting/SMOTE for the
CRITICAL class, richer feature engineering (e.g. rolling per-corridor
average delay, weather × rush-hour interaction terms), and possibly
collapsing to a coarser 2–3 class target if 4 classes proves too fine-
grained. I deliberately didn't pre-bake the dataset to hit 0.80 directly —
doing so would just be curve-fitting the data to the target rather than
giving you a dataset your model has to genuinely learn from, and an
examiner would spot a suspiciously easy 0.95+ F1 on synthetic data
immediately.
